Send an ArrayBuffer to a Clincoo Worker as Transferable

Copying a large buffer with structured clone doubles memory. Transfer moves ownership.

This article is available in: Indonesia · English

A Clincoo page that processes raw audio or image data often sends a Float32Array to a worker. Default postMessage copies the whole buffer. Two copies live until GC — on a visitor phone the preview tab can run out of memory.

Use the second argument: worker.postMessage(buffer, [buffer]). After transfer, byteLength on the main thread becomes 0. The worker owns the only copy. When the result is ready, transfer it back the same way.

Do not transfer a buffer still used by canvas or AudioContext. Detach makes the next operation throw. Copy into a work buffer first, or design a one-way flow: the page releases, the worker processes, the page receives a new result.

Test in editor.clincoo.buzz with a multi-megabyte file. Open the DevTools memory panel. Without transfer the heap jumps twice. With transfer the spike is close to one buffer.

Clincoo serves a static site. All memory cost sits in the visitor browser. Transferable is the cheapest way to send large data to a worker without doubling RAM.
