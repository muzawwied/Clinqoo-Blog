How to Set Up Project Webhooks in Clincoo

Webhooks are Clincoo's official notification channel: they tell your own systems automatically whenever an important event happens in your project, such as a successful ClincooPay QRIS payment or a finished deploy. Without webhooks you would have to open the Clincoo dashboard and check one by one whether a new transaction or a new site version exists. With webhooks, the notification is delivered straight to your endpoint the moment the event happens, and your system can react on its own: send the buyer a confirmation, record the transaction in your own database, or trigger whatever job was waiting for a signal from Clincoo. Webhook settings apply per project and live in the Webhook tab of the project Settings page on app.clincoo.buzz. This guide walks through registering an endpoint, choosing a delivery method, reading payment and deploy notifications, and making sure an incoming notification really came from Clincoo.

Register the receiving endpoint

Open your project on app.clincoo.buzz, go to Settings, and select the Webhook tab. Click Add, then fill in the endpoint URL that will receive the notifications, for example the address of your own backend or a webhook URL provided by an automation service. The URL must be HTTPS and publicly reachable from the internet; Clincoo never sends notifications to localhost, internal IP addresses, or endpoints that demand a login before accepting a request. You can register more than one URL at a time and remove any of them later from the same list, so switching systems never changes the payment flow on your deployed site. Type the address carefully: a single wrong character means notifications go somewhere else or never arrive at all, and Clincoo does not flag endpoints that fail to receive. Before going live, test your endpoint with a sample request from any tool you like.

Pick the GET or POST delivery method

Every URL in your webhook list has its own delivery method option, GET or POST, so you can mix both depending on what each endpoint can handle. For ClincooPay payment notifications, Clincoo always sends the data as a POST request with a JSON body, so payment endpoints must be ready to read that request body. GET is better suited to simple endpoints that only need to know an event happened, without the details. Whatever you choose, make sure your handler replies quickly with a success status as soon as the request arrives, then does the heavy work, like sending e-mail or writing to a database, in the background. An endpoint that answers slowly risks being treated as failed by the sender. Never put secrets in the URL itself, because receiving servers log full URLs.

ClincooPay payment notifications

When a buyer completes a QRIS payment on your deployed site, Clincoo sends a payment.paid event to your project payment webhook URL. The request arrives as POST with a JSON header and a single object carrying the transaction identity, as shown in the table below. Note that a ClincooPay QRIS expires after 15 minutes; if the payment lands in the final minutes, the webhook still fires and the transaction is still marked paid, so do not reject notifications that arrive close to the deadline. Store the incoming order_id to reconcile it with the transactions in your own system.

FieldContentNotes
eventpayment.paidMarks this as a successful payment notification
order_idTextThe ClincooPay transaction identity, used to match it with your own transaction
amountNumberThe payment value that was received
descriptionTextTransaction notes, including markers of the payment origin
statuspaidFinal transaction status at the time the notification was sent
paid_atUTC timestampThe moment the transaction was settled

Deploy event notifications

The same Webhook tab holds a deploy notification setting you can switch on or off per project. When enabled, your endpoint receives a notice every time the project deployment finishes, so your system always knows which version is currently live on the internet. The most common uses: purging caches of content that changed with the deploy, recording the version in an internal log, or letting your team know the site was updated without anyone opening the Clincoo dashboard. If you experiment with the settings, remember that a change only applies to the project where you made it, not to every project in your account. Deploy notifications also work well as a trigger for follow-up automation, for example running a quick check against the freshly deployed site.

Verification and troubleshooting

Notifications are sent by Clincoo's systems, not by the buyer, so make sure nobody else can abuse your endpoint: validate the payload structure carefully and never process a request whose format deviates. The most common mistakes: a URL that is not HTTPS yet, an endpoint that answers so slowly it is treated as failed, or a URL registered on the wrong project so the notifications never match the transactions you expect. If nothing arrives, check the receiving side's logs first before changing anything, then compare them against the transaction history in the Clincoo dashboard. For other common issues, start from Common Problems and Solutions, while the technical details of the payment flow and callbacks are in the ClincooPay API reference.
