Understand CORS Preflight before Clincoo Fetch Hits Another Domain

An Authorization header or JSON Content-Type triggers OPTIONS. Without matching Access-Control-Allow-* headers, Clincoo fetch fails quietly.

This article is also available in: Indonesia · English

A site deployed from Clincoo calls an API on another domain. The console shows blocked by CORS policy even though the endpoint opens in a new tab.

MDN CORS explains the OPTIONS preflight for non-simple requests. Content-Type application/json and an Authorization header almost always trigger preflight.

web.dev lists the required response headers: Allow-Origin, Allow-Methods, Allow-Headers. Do not set mode no-cors just to hide the error; the body becomes opaque and cannot be parsed.

In editor.clincoo.buzz, first test a GET with no custom headers. If that passes, add headers one at a time until preflight appears. Fix the server or use a same-origin proxy.

Clincoo does not disable browser policy. Understanding preflight saves hours of debugging on app.clincoo.buzz before you blame fetch.
