Check HTTP Status before Assuming a Clincoo Fetch Succeeded

fetch does not throw on 404 or 500. Check response.ok or status before parsing JSON in a Clincoo project.

This article is available in: Indonesian · English

In the Clincoo editor, many forms and data lists use fetch. The fetch promise only rejects on a network failure. A 404, 401, or 500 still lands in then, so response.json() may parse an HTML error page.

Keep the Response object first. If !response.ok, show the status and a short message, then return. Do not call json() immediately. This matches Fetch API docs: ok means status 200–299.

Separate network errors from application errors. Network failures hit catch. HTTP statuses appear after a Response arrives. Visitor copy should differ: try again later versus fix the fields or sign in again.

Test in Clincoo preview with a wrong URL and with an endpoint that returns 500. Open the Network tab: check status, Content-Type, and body. Do not rely on the console alone.

A status guard stops one broken endpoint from taking down the page. Only after the status is safe should you parse JSON and fill the DOM. Clincoo does not wrap fetch for you; this check stays in page script.
